# protocol transport v1

**Status:** frozen for implementation protocol v1

This document freezes the Phase 3 outer transport and headless relay decisions
used by the v1 implementation. It supplements, and does not replace,
`docs/approved-specification.md` and the Phase 2 cryptographic encodings.

## transport boundary

- Remote connections use TLS. The supplied client and server SSL-context helpers
  require certificate verification and set TLS 1.2 as the minimum version.
- Plain TCP is permitted only when the server is explicitly created with
  `allow_plain=True` and bound to a loopback address. The headless client applies
  the same loopback restriction when plain mode is requested.
- One TCP connection carries hello, access proof, display reservation, board
  traffic, live-session traffic, and heartbeats.
- There is no automatic TLS-to-plain downgrade.

## outer frame encoding

Every outer frame is one compact UTF-8 JSON object followed by one LF byte.
The complete encoded frame, including the LF terminator, is at most 16,384
bytes in protocol v1.

The codec is deliberately strict:

- the top-level value must be a JSON object;
- duplicate object keys are rejected at every nesting level;
- NaN and infinity are rejected;
- raw CR, LF, and NUL characters are rejected in string values;
- malformed UTF-8 and malformed JSON are rejected;
- a frame must contain exactly one LF terminator and may not contain another
  physical line;
- binary fields use canonical unpadded URL-safe Base64;
- request IDs are short ASCII strings generated by the requester;
- frame version is the integer `1`;
- field ordering is not semantically significant, but the implementation emits
  compact JSON using sorted keys for deterministic diagnostics and testing.

Malformed or oversized frames close the connection after a generic protocol
error where a response can safely be sent.

## operational frame-size validation

The protocol maximum is 16 KiB. The implementation refuses an operator
`max_frame_bytes` below 12 KiB because one otherwise-valid maximum board record
must remain representable after JSON and Base64 expansion. This is an
implementation safety check on the configurable operational limit, not a change
to the 16 KiB protocol maximum.

## request and response convention

Client requests contain:

```text
v
 type
 request_id
 ...type-specific fields
```

Normal responses use the same neutral `type` and echo the same `request_id`.
Unsolicited server events do not carry a request ID. Generic failures use an
`error` frame with a neutral error code; error frames do not disclose phrases,
keys, plaintext, ciphertext bodies, or raw IDs.

## connection state

The server accepts request-bearing frames in this order:

```text
hello
  -> access_proof
  -> display_reserve
  -> board/session requests
```

Any attempt to skip a required state is a protocol-state failure.

### hello

The client sends protocol version, client version, capabilities, and a request
ID. A compatible server returns:

- protocol version;
- persistent server ID;
- current access generation;
- server time;
- active operational limits;
- heartbeat interval;
- one fresh access challenge.

An unsupported protocol version is rejected before access-phrase processing.

### access proof

The client sends the Phase 2 `client_nonce` and access HMAC proof. A challenge is
one-use. Failed access attempts are rate-limited per observed peer address; the
response is deliberately generic.

### display reservation

After access succeeds, the client sends only its 16-byte opaque display token.
The raw three-character display ID is never sent to the relay. Active
collisions are rejected. A disconnected reservation is retained as an
in-memory lease for the configured lease interval, then expires.

## board protocol

### stored record fields

A routed board record contains only:

- `message_id`;
- opaque `display_token`;
- server `created_at`;
- server `expires_at`;
- encrypted `ciphertext`.

The relay does not receive board plaintext or a raw display ID.

### board list pagination

A 24-message board containing maximum-size records cannot fit into a single
16 KiB JSON frame. Protocol v1 therefore represents the canonical board list as
an internal paginated snapshot while preserving the product model of one list.

The client requests `board_list` with an integer `offset`. After the first page
it also sends the returned `snapshot_sequence`. Each page returns:

```text
sequence
restart
offset
next_offset
done
records
```

The server dynamically packs as many complete records as fit under the active
frame limit. If the board publication sequence changes between pages,
`restart=true` tells the client to discard the partial snapshot and start again.
The headless client makes at most a bounded number of snapshot restarts.

After the final page, the client sends `board_subscribe` with
`after_sequence=sequence`. Subscription succeeds only if the sequence is still
current. Otherwise the client restarts the canonical snapshot. This closes the
race between the last list page and live subscription.

### live sequence rules

`board_update` and `board_remove` are unsolicited events with monotonically
increasing in-memory publication sequence numbers. Each broadcast mutation
event consumes one sequence number.

When a post at capacity evicts an old record, the remove event is published
first and the accepted update second. A client that observes a sequence gap
reloads the canonical board rather than attempting complex reconciliation.
The sequence is publication state, not persistent message state, and therefore
resets on normal server process restart.

### board persistence

SQLite stores current ciphertext records and posting cooldowns. Posting uses one
`BEGIN IMMEDIATE` transaction covering expiry cleanup, duplicate checking,
cooldown checking, insertion, cooldown update, capacity eviction, and commit.

Protocol v1 also persists opaque `board_seen_ids` tombstones for the current
access generation. Phase 2 derives a unique board key from `message_id` and then
uses a fixed AEAD nonce. Consequently, a message ID must never be accepted twice
under the same access generation, even if the first record has expired or was
evicted. Tombstones enforce the approved duplicate-message-ID rule without
storing plaintext. Access rotation must clear them together with the board and
cooldowns.

## live-session routing

Only access-authenticated, display-reserved connections may use session frames.
The server routes opaque room IDs and authenticated-handshake material but does
not know the comm phrase, raw IDs, final session keys, verification code, or
plaintext.

### waiting and pairing

`session_wait` contains the opaque room ID plus the creator's public handshake
nonce/key. The room exists only in memory and expires after the configured wait
timeout.

`session_join` contains the same fields for the joiner. The first valid joiner
consumes the waiting room and receives a server-random 16-byte pair ID. Both
parties receive a neutral `session_pair` event containing their role and the
peer's public handshake material. A third user cannot join the active pair.

Unavailable, expired, occupied, mistyped, or rate-limited joins are represented
through the same unsuccessful join result at the client boundary.

### handshake forwarding

Each side computes and sends its Phase 2 role-bound phrase proof in a
`session_handshake` request. The server does not and cannot verify the phrase
proof; it only enforces pair membership, one proof per role, and the handshake
timeout, then forwards the opaque proof to the peer.

A route becomes eligible for encrypted data only after both sides have submitted
one proof. If a client rejects the peer proof, it sends a generic route close so
server memory is not left paired.

### encrypted data

`session_data` contains:

- pair ID;
- opaque session ID;
- direction label;
- 64-bit counter;
- encrypted body.

The relay enforces pair membership and that the sending role uses the correct
direction. It latches the first opaque session ID for the pair and requires it
for later frames, but it does not inspect counters or ciphertext contents; those
security checks belong to the Phase 2 end-to-end channel at the receiving
client. Comm frames are never written to SQLite.

### close and cleanup

The official client first sends the Phase 2 encrypted close event where
possible, then sends a generic `session_close` routing request. Disconnect,
waiting timeout, handshake timeout, or route close releases the in-memory pair.
There is no offline queue or session resumption.

## heartbeats and bounded memory

- Server heartbeat interval defaults to 30 seconds.
- A connection is considered dead after 90 seconds without valid activity.
- Client and server both handle `ping` and `pong` frames.
- Every connection uses a bounded outbound queue; the default bound is 64
  complete frames.
- A slow consumer is disconnected rather than allowing unbounded relay memory.
- Dead connections release their live session/waiting state and convert an
  active display reservation into an expiring lease.

## rate limits

Phase 3 implements the approved defaults:

- access failures: five per ten minutes per peer address, followed by increasing
  delay;
- comm join attempts: twenty per ten minutes per peer address.

These limits are operational abuse controls and do not claim persistent human
identity.

## frozen Phase 3 implementation choices

The following details are now compatibility-sensitive for protocol v1:

1. one LF-terminated compact UTF-8 JSON object per outer frame;
2. strict duplicate-key and non-finite-number rejection;
3. canonical unpadded Base64url for binary fields;
4. same neutral type plus echoed request ID for ordinary responses;
5. sequence-consistent paginated `board_list` snapshots;
6. remove-before-update sequencing for capacity eviction;
7. opaque spent-message-ID tombstones for an access generation;
8. server-random 16-byte pair IDs;
9. server forwards but does not verify comm phrase proofs;
10. bounded per-connection outbound queue, with disconnect on overflow.

Changing one of these compatibility-sensitive rules requires an explicit
protocol review rather than an informal wire change.
